## Findings

1. **HIGH integration gate — the required learner action cannot yet change authoritative movement or service.** `services/dashboard_api/server.py:55-56` returns 405 for every POST; `web/app.js:330-340` only advances saved frame indices, and `services/dashboard_api/replay.py:1,24-70` reads immutable frames. Thus a learner cannot dispatch, advance server time, accept a new closure, reroute from an underway position, or cause a ledger-counted service through this UI. The seven fixture frames are explicitly constructed (`fixtures/replay_ui/paradise_mock.json`, `services/dashboard_api/CHECKPOINT.md:7,30`), so this is an **incomplete product integration**, not an implementation defect in a deliberately read-only replay adapter. Keep the mock label. Integrate a root-owned action endpoint that validates a requested dispatch/step/closure against the authoritative snapshot, advances route/trip/ledger server-side, and returns a new snapshot; have both views display that record. Exercise dispatch → movement → observed closure → feasible reroute/stranding → actual counted arrival/delivery with a saved server trace before claiming the required feature.

2. **MED — OSM destination restriction is lost in the routable graph.** `services/geography/importer.py:46-47,63-80` treats every access value except `no`/`private` as open. An OSM service way tagged `access=destination` yields two directed edges with `vehicle_access.bus=true` in the pinned repro, allowing it as a through route. `access=destination` permits access to the destination but restricts through traffic; flattening it to a boolean can make a dispatch route use a road whose access condition it does not satisfy. Preserve the conditional access value and evaluate it with trip origin/destination and vehicle policy during route search, or exclude it until that policy exists. The same logic drops a mode-specific `bus=yes` override when `access=no`; whether an aid bus qualifies as OSM `bus` requires an explicit jurisdiction/use policy, so preserve the tags without automatically declaring a rescue bus eligible. Official tag semantics: [OSM access](https://wiki.openstreetmap.org/wiki/Key:access), [destination](https://wiki.openstreetmap.org/wiki/Tag:access=destination), [bus](https://wiki.openstreetmap.org/wiki/Key:bus). Repro: `repro2.log` lines `destination-restricted edge_count 2 bus_access [True, True]` and `bus-exception edge_count 0`.

3. **HIGH provenance/data-integrity defect — ingestion can certify geometry outside the declared AOI as Paradise.** Initial `services/geography/ingest.py:7-9,14-33` and cloud `cf5251` `ingest.py:88-112` both accept the default Paradise bbox, origin and label for an arbitrary input file without verifying that the source response covers that bbox or that any road intersects it. The newer code computes separate feature and viewport bounds, but still marks roads available from the unrelated source. At exact `cf5251`, a two-node road at `(0,0)` produced `label='Paradise, California'`, `roads=1` and `ReplayStore.coverage(39.754,-121.607).available=True` (`repro-maps-latest.log`, exit 0). The map can therefore certify Paradise coverage when its sole road is elsewhere. Before setting any layer available, verify the requested source bbox and at least one relevant feature inside or crossing the declared acquisition AOI; reject or quarantine unrelated geometry. The actual committed OSM fixture has an internally consistent API bbox and hashes, so this is a boundary-validation defect, not a claim that the current fixture itself is out of area.

4. **MED cross-view contract mismatch — valid metric geometry cannot pass the 3D scene validator with its emitted CRS label.** The Maps importer emits metric `geometry_m` and `metric_crs='local equirectangular metres; origin_lonlat is WGS84 longitude,latitude'` (initial `services/geography/ingest.py:32-33`, cloud `cf5251` `ingest.py:111-112`). `viewer3d/scene.py:293-295` rejects any `metric_crs` string containing `wgs84`, even when it describes the separate geographic origin rather than the coordinate units. Constructing a `SceneInput` from that emitted metadata fails with `ValueError: metric CRS required, not longitude/latitude` (pinned `repro2.log`). Define a machine-readable metric CRS identifier and separate WGS84 origin fields in the root adapter, verify the geometry actually uses metres, then feed a normalized metric-only CRS declaration into `SceneInput`. This is fixable at the integration boundary without weakening the 3D rejection of degree coordinates.

5. **MED — failed native rendering can detach an existing PNG from its sidecar.** The AMD follow-up's `viewer3d/render.py:343-352` preserves an existing PNG on a failed call but always replaces its adjacent `.json` with metadata for the *failed new frame*. A CPU fake-context repro started with `frame.png` plus a successful `prior-frame-hash` sidecar, then attempted `new-frame-hash` while EGL creation raised. The prior PNG bytes remained, while `.json` became `status=failed`, `snapshot_hash=new-frame-hash` (`repro-amd.log`, exit 0). An audit or replay reader can no longer pair the surviving image with its correct authoritative frame. Publish image and success sidecar as one coordinated update, and write failure diagnostics to a separate attempt file; keep both existing outputs untouched on failure.

6. **MED inferred renderer visibility defect — coincident road, route and trail lines can occlude later layers.** `viewer3d/render.py:87-90,313-334` preserves exact supplied line vertices and draws roads before routes before trails with depth testing enabled (`:304`). Its own test fixture deliberately gives all three the same vertices and z (`viewer3d/tests/test_render.py:22-33,49-51`). The code never changes the depth function for later lines or gives them a line-specific depth bias; `ctx.polygon_offset` is set only for the triangle pass (`:314`). Standard OpenGL initially uses `GL_LESS`, so equal-depth route/trail fragments can fail after the road line has populated depth. This is a **source-level inference**, not an observed native image: the new tests use a fake ModernGL context and no EGL/GPU rasterization occurred. Render overlays with a documented depth policy, then verify a coincident road/route/trail fixture in a real saved image once graphics prerequisites and a lease permit it. See [Khronos depth function](https://wikis.khronos.org/opengl/GLAPI/glDepthFunc) and [ModernGL depth settings](https://moderngl.readthedocs.io/en/stable/reference/context.html).

## Product and evidence boundaries

- Maps `ReplayStore.frame_hash` (`services/dashboard_api/replay.py:9-11`) hashes the complete serialized **view frame** excluding `snapshot_hash`. That does not establish the shared authoritative snapshot identity required by `handoff/CONTRACTS_V1.md` and `docs/PATHFINDING_AND_TRACKING.md`. Root should carry one authoritative `snapshot_hash` unchanged into both views and compute a separate normalized `view_hash` for each projection. `viewer3d/scene.py:17-22,90-104,133-142` accepts a typed `FrameIdentity` and returns matching `PreparedScene`, but has no transport adapter or shared-envelope validation. Route/trip/time provenance must be mapped from authoritative records; the scene descriptor cannot create it.
- Earlier Maps heads `82ce6bb` and `ed96513` report failed acquisition and zero roads/edges. The published `cf5251` head **does contain real bounded OSM geometry**: `fixtures/geography/paradise/raw.osm` SHA256 matches `source_manifest.json:10`, the graph source hash matches, the manifest identifies the OSM API bbox and observed timestamp range 2007-10-25 to 2026-09-09, and the generated area has 444 road ways, 199 buildings, 40 landuse ways, 3,046 graph nodes and 5,959 positive-time edges (`maps-source.log`). The map UI now displays OSM attribution and keeps route/fire overlays visibly labeled constructed. It does not display the source observation/date in the visible map panel (`web/app.js:76-106,150-181`), so a visible source-date label remains to add. A calculated route on this graph and an authoritative route/trip/ledger chain remain unproven. The source manifest and geometry checks prove file consistency, not live or current incident coverage.
- Initial AMD `74ffaac` has CPU scene descriptors only. Follow-up `986bb3` adds `viewer3d/render.py` and a caller-invoked EGL renderer, but `viewer3d/README.md:63-94`, `platform/HANDOFF.md:17-29`, `platform/graphics_probe.py:105-112`, and `evals/fsr4/EXPERIMENT_PLAN.md:1-3,17-19` accurately say that runtime acquisition failed and no real native render, GPU context, FSR4 provider/ML dispatch or graphics result was produced. Genuine same-server FSR4 and product ROCm execution remain separate unresolved gates. A provider label, replay preparation or FSR3 fallback must not be counted as FSR4. No graphics lease was used in this review.
- The published follow-up `services/dashboard_api/export_preview.py:9-38` embeds saved bootstrap/frames/CSS/JS into a labeled static HTML preview and escapes `<` in embedded JSON. Its coverage endpoint explicitly reports no live query. The tests cover embedding and a script-breakout string. I found no additional high/medium defect in that delta; its 18-test API suite passed, but those tests do not establish live server action or 3D rendering. The owner checkpoint records Chrome saved-preview inspection of first/closure/final frames; this reviewer did not independently inspect them.
